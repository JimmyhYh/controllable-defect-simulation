## 二、身份口径与绑定

每条实际来源记录同时保存以下四个字段；不要把它们压成一个含义不明的RGB hash：

| 字段 | 定义与核验用途 |
| --- | --- |
| `file_sha256` | 原PNG文件全部字节的SHA256。实际取得时必须与旧manifest的`sha256`一致；D_fit还须与固定角色的`file_sha256`相等，旧N／N_gen则核冻结split与manifest路径绑定。字节数、原模式和1024×1024尺寸也必须相符。 |
| `legacy_rgb_group_id` | 逐字复制旧manifest的`rgb_content_sha256`；在D_fit中还须与冻结角色的`rgb_sha256`相等。只用于继承分组、排除与角色绑定，不解释历史序列化。 |
| `decoded_RGB_u8_sha256` | 对本次`Image.convert('RGB')`后的1024×1024×3、uint8、HWC、C连续原始RGB字节作SHA256，不加头；同时保存shape、dtype、通道顺序和序列化说明。 |
| `working_RGB_sha256` | 对规范256×256×3 float32 C连续RGB调用冻结`inputs.working_rgb_identity`，其摘要包含dtype／shape／C头及数组字节。用于工作内容碰撞和模型输入去重。 |

两种新摘要与旧组ID**既不要求相等，也不要求不等**；禁止尝试不同头、通道顺序或算法去凑旧值。旧组排除关系仍按冻结角色与元信息闭合；新增摘要不触发重新抽样或修改旧分组。

实际工作预处理严格为Pillow RGB uint8双线性缩到256，再转float32除以float32(255)，不拉伸对比度，不改为原始float图的另一种插值链。RGBA仍沿用既定convert('RGB')语义，不借本补充新增alpha筛选或其他图像适用性门槛。

`sources.json`绑定：准备complete及其8项输出、原设计、旧manifest／两split、失败实现与失败JSON、停诊报告、本补充静态正文、新generation_v2.py、封存三源码、解释器及依赖元信息。总执行计划是可变进度文档，不把其整份hash作为运行准入，否则同步进度会错误地破坏缓存身份。相关固定来源由准备sources继承，不改其中任何值。
