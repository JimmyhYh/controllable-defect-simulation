## 三、静态AST核验（7项全通过）

1. 模块顶层不导入Torch
2. 无 `.train()`／`.step()`／`zero_grad`／`backward` 调用
3. 无 `running_mean`／`running_var`／`num_batches_tracked` 赋值（不写缓冲）
4. 存在 `_batch_stat_normalization` 作用域函数
5. 作用域以 `finally` 恢复原 `forward`
6. 原生调用形如 `batch_norm(x, None, None, w, b, training=True, …)`
7. `run_diagnostic` 内顺序：事务(322) < Torch环境(333) < 构造(336) < 状态hash(341) < 干预作用域(365)

第7项为源码行号，直接证明"事务先于Torch导入""替换在构造与状态hash校验之后"。

## 四、干预实现要点

- 作用域内把 `dec_head[1].forward` 替换为闭包，内部调用
  `F.batch_norm(x, None, None, weight, bias, training=True, momentum=0.0, eps)`；
  因两个 running 参数均为 `None`，不产生也不写任何缓冲。
- `finally` 中 `del module.__dict__["forward"]` 让类方法重新生效，并断言 `module.forward.__func__` 回到原函数。
- 逐图在替换函数内计算 `max_c|μ−running_mean|`、`max_c|σ²/running_var−1|`、中位数、最大通道号与有限性，写入探针；这既是3.4第2项断言，也是"两个臂真的不同"的证据。
- 每次前向后校验：生效计数 == 序号+1、两项差异有限且 >1e-6、`training=False`、`track_running_stats=True`。
- 收尾校验：生效21／恢复1、`state_dict` hash 等于 `1513a3df…`、三个缓冲逐位不变。
